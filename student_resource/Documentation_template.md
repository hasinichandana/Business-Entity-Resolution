# 1. Executive Summary

The Amazon ML Challenge 2026 Business Entity Resolution task requires matching business records from Source 2 and Source 3 with the corresponding reference entities in Source 1.

The challenge allows different relationship types between entities, including:

- One Source 1 entity having no matching record
- One Source 1 entity having one matching record
- One Source 1 entity having multiple matching records

The solution developed for this task follows a multi-stage entity-resolution pipeline.

The pipeline performs data normalization, country-aware candidate generation, semantic retrieval, feature engineering, machine-learning-based matching, and entity-level decision making.

The solution combines textual, semantic, address, token-level, and character-level information to identify records that are likely to represent the same business.

The final predictions are stored in:

- `output/matching_results.tsv`
- `output/candidate_pairs.tsv`

# 2. Methodology

## 2.1 Problem Analysis

Business records can represent the same real-world entity while containing differences in:

- Business names
- Spelling
- Abbreviations
- Address formatting
- Postal information
- Numeric information
- Country-specific terminology
- Word ordering
- Token representation

Therefore, exact string matching alone is insufficient for reliable entity resolution.

The task is formulated as a record-linkage problem where records from Source 2 and Source 3 are compared against Source 1.

The evaluation emphasizes precision through the F0.5 measure, where precision has greater importance than recall.

The solution therefore focuses on generating high-quality candidates and making entity-level matching decisions that balance precision and recall.

# 3. Candidate Generation (Blocking)

Comparing every Source 1 record with every Source 2 and Source 3 record would result in a very large number of comparisons.

Candidate generation is therefore used to reduce the search space.

The solution uses country-aware candidate generation together with semantic retrieval.

For each Source 1 entity, the system retrieves a limited number of promising candidates from Source 2 and Source 3.

The configured candidate count is:

K_CAND = 20

This means that up to 20 candidates are considered per Source 1 entity for each relevant source during semantic retrieval.

The pipeline also evaluates blocking quality using recall at different candidate values.

Country information is incorporated into candidate generation to reduce comparisons between geographically incompatible records.

The candidate pairs generated by this stage are stored in:

output/candidate_pairs.tsv
# 4. Feature Engineering

After candidate generation, features are calculated for each Source 1 to Source 2/Source 3 candidate pair.

The solution combines multiple types of information.

# 4.1 Business Name Features

Business names are compared using character-level and token-level similarity information.

The feature generation considers variations caused by:

Spelling differences
Token ordering
Abbreviations
Shared tokens
Character-level differences
# 4.2 Address Features

Address information is incorporated into the matching process.

The system considers similarities between address components and textual representations, including postal and numeric information.

# 4.3 Semantic Features

Semantic representations are generated using a Sentence Transformer model.

The embeddings are used to retrieve semantically similar business records even when their textual forms are not exactly the same.

# 4.4 Token Features

The pipeline also calculates token-level information.

These features capture:

Shared tokens
Token rarity
Token genericness
Name-token relationships

Country-independent token statistics are used so that previously unseen country vocabulary can receive fallback values instead of requiring a predefined country list.

# 4.5 Character Similarity

Character-level similarity is calculated using RapidFuzz-based similarity functions.

Jaro-Winkler and related string-distance information are used for comparing business names and other textual fields.

# 4.6 Cross-Record Features

The pipeline also considers relationships between candidate records from different sources.

These include similarity information between S2 and S3 records where applicable.

# 5. Matching Model

The main machine-learning matching model is XGBoost.

The candidate-pair features are supplied to the XGBoost classifier to estimate the probability that a candidate pair represents the same business entity.

The training process uses grouped cross-validation based on Source 1 entities.

The configured number of folds is:

N_FOLDS = 3

Grouping by Source 1 prevents records belonging to the same reference entity from being arbitrarily distributed across training and validation groups.

The model uses early stopping during training to determine an appropriate number of boosting iterations.

A second-stage model is also available in the pipeline and is retained when it improves out-of-fold performance.

# 6. Decision Making

The model probabilities are not directly converted into final matches using only a simple global threshold.

The solution evaluates entity-level decisions because each Source 1 entity can have zero, one, or multiple matching records.

The pipeline considers the F0.5-oriented evaluation objective when selecting the final matching records.

Probability calibration and expected-F0.5 decision logic are incorporated into the decision process where the corresponding configuration is selected based on validation performance.

This allows the system to make decisions at the Source 1 entity level rather than treating every candidate pair as an independent final prediction.

# 7. Handling Multiple Matches

The competition allows one-to-zero, one-to-one, and one-to-many relationships.

The solution therefore does not force every Source 1 entity to have exactly one match.

The final decision process can produce:

Source 1
   |
   +---- No matching entity

or

Source 1
   |
   +---- One matching entity

or

Source 1
   |
   +---- Multiple matching entities

This is important because forcing exactly one candidate for every Source 1 entity could create false positive matches.

# 8. Country and Open-Set Handling

The training and test data can contain different country distributions.

The pipeline therefore avoids relying on a fixed hard-coded list of countries for its token and normalization logic.

Country-aware blocking is used where appropriate during candidate generation.

For unseen countries, token statistics can fall back to default values rather than failing because the country was not present during training.

This design allows the matching pipeline to handle previously unseen country vocabulary more robustly.
